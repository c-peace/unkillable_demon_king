# Advanced L2 Harness and RAG Design

Last updated: 2026-08-21 (Asia/Seoul)

Status: target architecture inferred from organizer rules, L2 guidance, MCP capabilities, the public HealthBench paper, and the public `simple-evals` execution interface. This is a general medical-response design, not a benchmark-specific strategy.

## Intuitive principle

**Let L2 make the medical judgment and write the answer; let the harness deterministically protect conversation state, decide how far the workflow may escalate, control evidence retrieval, and verify provenance.**

The target is a risk-adaptive state machine, not an unconstrained agent loop and not an always-on RAG pipeline.

## Non-negotiable constraints

- The service is OpenAI-compatible and uses the request `messages` as the authoritative conversation state.
- The transport is stateless. No hidden server-side session memory is required for correctness.
- Every returned user-facing answer is generated by Lunit L2.
- Retrieval and generation have separate prompts and tool exposure.
- Evaluation-time execution must not require public internet access; organizer-internal L2/MCP access remains subject to confirmation.
- Raw conversation history remains available even when a derived state representation is used.
- No benchmark-item matching, rubric reconstruction, grader imitation, or hidden-set inference is permitted.

## Target flow

```text
OpenAI-compatible request
  -> request validation and deadline
  -> conversation compiler
       -> immutable role-labelled raw transcript
       -> request-local clinical state with turn provenance
  -> response controller
       -> DIRECT lane
       -> CLARIFY lane
       -> GROUNDED lane
       -> HIGH-RISK lane
  -> generation L2
       -> direct answer, or
       -> retrieve_relevant_content(self-contained query)
            -> source-family router
            -> retrieval L2 + selected MCP tools + finalize_retrieval
            -> evidence registry and claim/evidence verification
            -> compact evidence packet
       -> grounded draft
  -> conditional quality review
       -> pass, or
       -> final L2 revision
  -> response validation and OpenAI-compatible envelope
```

## Progressive execution lanes

### DIRECT

Use when the conversation already contains enough information and the answer is not materially dependent on a current source. Typical examples are explanations, empathetic communication, interpretation framed with appropriate uncertainty, or a follow-up answer grounded in the supplied conversation.

Expected path: one generation L2 call.

### CLARIFY

Use when a missing fact materially changes safety or the recommendation. Ask the smallest useful clarification while still providing any safe, immediately helpful information. Do not turn every underspecified question into an interview.

Expected path: one generation L2 call, no retrieval unless an immediate factual lookup is independently useful.

### GROUNDED

Use for specific guidelines, medicine safety or interactions, current approvals, reimbursement, coding, law, or other source-sensitive claims.

Expected path: generation L2 requests retrieval, retrieval L2 gathers bounded evidence, generation L2 writes the final response.

### HIGH-RISK

Use for dosing, interactions, contraindications, emergency triage, pregnancy/pediatrics, evidence conflicts, partial retrieval, or long conversations where derived state was required. Add a structured evidence check and conditional L2 review/revision.

Expected path: grounded path plus verifier and, only when issues are found, one final L2 revision.

The lane policy must be configurable and evaluated. Development time may be abundant, but model calls, evaluator deadlines, and MCP rate limits are not yet known.

## 1. Conversation compiler

### Raw transcript

Preserve every supplied message with role and stable turn number. Because L2 is described as single-turn optimized, support a configurable representation that flattens the conversation into one role-labelled case packet while keeping the final user turn explicit. Compare this with native multi-message pass-through.

Do not summarize ordinary HealthBench-sized conversations by default. Full context is safer than lossy compression when it fits.

### Clinical working state

For longer or high-risk conversations, derive a request-local structure containing:

- current user intent and requested output format;
- user role/expertise, language, jurisdiction, and resource constraints;
- demographics and pregnancy status when supplied;
- symptoms, onset, duration, severity, trajectory, and associated findings;
- diagnoses, medications, doses, adherence, allergies, vital signs, and tests;
- prior assistant claims, user corrections, and unresolved references;
- known facts versus uncertainty or missing decision-critical facts;
- safety signals and possible escalation needs.

Every extracted field should carry turn provenance. The structured state supplements the raw transcript and must never silently override it. If extraction is uncertain or contradictory, preserve the conflict rather than selecting a convenient value.

The context compiler may use a structured L2 call if supported reliably. Its output must be schema-validated, and failure falls back to the raw transcript rather than failing the request.

## 2. Response controller and plan

The controller selects a lane and, when grounding is required, creates atomic claims or questions that need evidence. A useful internal plan contains:

- answerability and clarification need;
- risk class;
- user/audience and desired depth;
- jurisdiction and time sensitivity;
- claims requiring evidence;
- preferred source families;
- maximum retrieval and review budget.

Do not expose this internal plan or chain-of-thought to the user. Prefer a structured terminal tool/schema over free-form planning text if L2's tool-calling API proves reliable.

Start with the generation L2's native decision to call `retrieve_relevant_content`. An explicit controller call is an optional advanced module and must demonstrate better aggregate quality than its added latency and failure surface.

## 3. Claim-driven adaptive RAG

Retrieval should answer explicit self-contained evidence questions, not simply search the final user message. Resolve references such as “that drug,” “the previous dose,” and “is it covered here?” from the conversation before retrieval.

When several independent current facts are required, split them into a small set of atomic tasks. Run independent tasks concurrently only within measured MCP rate and deadline limits.

### Source hierarchy

| Need | Preferred source family |
| --- | --- |
| Clinical guideline recommendation | Guideline `index_*`: discover document/section, then read bounded original pages |
| Official drug-label safety or interaction | `adr_retrieve_drug_info` / DailyMed |
| Korean approval, indication, dose, warning | `openapi_mfds_*` |
| Korean reimbursement, notice, or oncology regimen | `hira_updates_search`, HIRA OpenAPI, or HIRA index |
| KCD coding or billing-code validity | `kcd_*`, then HIRA validation where applicable |
| Korean statutory rule | `openapi_law_*`: search, list relevant article, retrieve exact text |
| Research evidence | `rag_vector_query` over PubMed abstracts as supporting evidence |
| Adverse-event signal | bounded FAERS SQL, explicitly treated as association rather than causation |

Prefer an authoritative purpose-built source over generic vector or SQL retrieval. Keep jurisdiction and source role explicit; approval, reimbursement, clinical recommendation, and observed adverse-event association are not interchangeable.

### Tool-family routing

The target design exposes a small relevant MCP family to retrieval L2 plus a broad fallback when routing confidence is low. This reduces tool-schema noise while preserving recall.

Maintain two ablatable modes:

1. all supported MCP tools exposed to retrieval L2, aligned with the model's described training; and
2. family-routed exposure with fallback.

Choose the production default only after measuring tool-call validity, evidence recall, latency, and answer quality. Do not route with benchmark-specific keyword tables.

### Retrieval loop

- Only retrieval L2 sees raw MCP tools and `finalize_retrieval`.
- Retrieval gathers evidence but never writes the final user answer.
- Enforce configurable limits for L2 rounds, MCP calls, per-tool timeout, total deadline, result size, and retry count.
- Accept the first valid `finalize_retrieval` terminal call.
- If the model does not finalize, deterministically return `partial` when usable citable evidence exists, otherwise `no_evidence`.
- Retry only transient failures; do not retry validation/schema errors indefinitely.

## 4. Evidence registry and provenance bridge

During retrieval, store every citable result in a request-local registry keyed by `cite_uid`. A normalized evidence item should contain, when available:

- `cite_uid`;
- source family, jurisdiction, title, URL, and date/version;
- compact supporting excerpt;
- originating retrieval task and tool call;
- which planned claims it supports, contradicts, or leaves unresolved;
- selection status from `finalize_retrieval`.

When retrieval ends, resolve selected `cite_uid` values against this registry and send only the compact selected evidence packet to generation. Reject or ignore unknown identifiers. Do not dump raw tool traces or entire documents into the generation context.

The `relevance_score` is a selection hint, not clinical confidence or proof strength.

## 5. Evidence verification

For high-risk or multi-source answers, verify the planned claims against selected evidence before final generation or revision:

- supported;
- contradicted;
- insufficient;
- source/jurisdiction mismatch;
- outdated or unclear applicability.

The verifier is not a simulated HealthBench grader. It is a generic grounding check. Deterministic validations should run first: every selected citation exists, every cited source was actually retrieved, required metadata is present, and evidence size limits hold. An L2 verifier may then assess semantic entailment and conflicts.

Never erase disagreement. Pass conflicting sources and applicability uncertainty to generation so L2 can explain them.

## 6. Generation L2

Generation sees:

- the immutable conversation transcript;
- the optional provenance-linked clinical state;
- the final user turn and requested format;
- the compact verified evidence packet, if retrieval occurred;
- one generation-only system prompt;
- only `retrieve_relevant_content` as a tool while retrieval remains available.

The prompt should state transferable medical-response behavior without mentioning HealthBench or its rubrics:

1. answer the actual question and honor the requested format;
2. use all relevant prior facts and explicitly repair important earlier errors;
3. distinguish evidence, inference, and uncertainty;
4. include decision-critical actions, contraindications, and red flags without boilerplate over-escalation;
5. adapt terminology, depth, geography, and available resources to the user;
6. lead with the direct answer, then provide concise reasoning, conditions, and next steps;
7. cite only claims supported by the supplied evidence packet;
8. ask clarification only when it materially changes a safe answer.

## 7. Conditional reviewer and final revision

Do not run an always-on free-form critic by default. Trigger review when one or more of the following applies:

- high-risk lane;
- medicine dose, interaction, contraindication, pregnancy, pediatrics, or emergency advice;
- evidence status is `partial`, conflicting, or source applicability is uncertain;
- a long conversation required clinical-state extraction;
- the response contains several source-sensitive claims;
- a structured task has strict fields or format requirements.

The reviewer returns a structured pass/revise decision across factual support, missing decision-critical content, conversation consistency, safety proportionality, clarity, requested format, and citation support. It must not produce benchmark-like scoring.

When revision is required, provide the draft, grounded issues, raw context, and evidence packet to a final L2 revision call. The returned content is still generated by L2. Limit the loop to one revision unless testing demonstrates a justified exception.

Candidate generation or multi-draft synthesis is an experimental high-cost module, not the default. Measure whether it improves reliability without causing verbosity or inconsistency.

## 8. Reliability and graceful degradation

Use a global request deadline and give each stage a remaining-time budget. Required fallback behavior:

- context extraction fails -> use raw transcript;
- controller fails -> use ordinary generation with retrieval available;
- tool-family route is uncertain -> expose broad fallback tools;
- MCP fails or times out -> generation receives `partial`/`no_evidence` and must not invent support;
- evidence verifier fails -> keep deterministic validations and selected evidence, mark semantic verification unavailable;
- reviewer fails -> return the valid L2 draft;
- final content is empty or contains unresolved tool calls -> retry L2 once within the deadline, otherwise return a valid error response rather than retrieval text.

Use bounded concurrency, transient-error backoff, circuit breaking, and per-stage cancellation. The service must never enter an unbounded tool or self-review loop.

## 9. Privacy-safe observability

Keep observability local to the container and avoid public telemetry. Record structured operational metrics without raw conversation or patient content:

- request/trace identifier and history hash;
- lane and whether context extraction/review was used;
- stage latency, L2 calls, MCP tool family/call count, retries, and timeout;
- retrieval status, evidence count, citation-validation result;
- response length and completion/error state.

Do not log API keys, raw tool authentication, full patient messages, or complete retrieved documents.

## 10. Evaluation and ablation strategy

Build synthetic, team-authored suites rather than copying benchmark examples:

- multi-turn reference resolution and correction of earlier assistant mistakes;
- preservation of negation, dose, duration, allergy, pregnancy, and time course;
- answer-versus-clarify decisions;
- proportional triage and red-flag coverage;
- guideline, medicine, MFDS/HIRA/KCD/law, and research-source routing;
- evidence support, citation integrity, conflict handling, and no-evidence calibration;
- user expertise, language, geography, and resource adaptation;
- structured health-data and format-following tasks;
- tool timeout, malformed calls, missing finalizer, empty response, and concurrency behavior.

Ablate at least:

- native multi-message input versus flattened role-labelled case packet;
- direct generation versus adaptive RAG;
- all-tool exposure versus family routing with fallback;
- raw transcript only versus raw transcript plus clinical working state;
- no verifier versus high-risk conditional verifier;
- one draft versus conditional revision;
- evidence count/context-size limits and retrieval budgets.

Track answer quality at aggregate capability level, together with latency percentiles, failure rate, tool-call validity, retrieval sufficiency, evidence utilization, unsupported citation rate, and multi-turn fact-retention accuracy. Use dashboard feedback only at aggregate capability level and never turn individual validation cases into rules.

## Delivery order

Even with ample development time, keep every layer independently testable and reversible:

1. evaluator-compatible stateless API, Docker, and generation-only L2 path;
2. exact full-history preservation and multi-turn representation experiments;
3. retrieval L2 loop, MCP client, terminal function, and evidence registry;
4. adaptive RAG and source-family routing with broad fallback;
5. clinical working state with provenance;
6. deterministic and semantic evidence verification;
7. conditional review and final L2 revision;
8. reliability controls, local tracing, synthetic evaluation, and systematic ablations;
9. enable only the modules that demonstrate net quality and reliability gains under measured runtime budgets.

## Explicitly rejected defaults

- always-on RAG;
- an unconstrained agent with all tools at every stage;
- raw retrieval output returned to the user;
- replacing raw history with a summary;
- hidden long-term memory required for correctness;
- public internet dependencies in the evaluation path;
- an always-on multi-draft or self-critique loop without measured benefit;
- benchmark-specific branches, case templates, or grader emulation.
